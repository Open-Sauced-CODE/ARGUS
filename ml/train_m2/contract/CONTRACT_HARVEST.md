# Phase 6 harvest contract (schema `m2.harvest.v1`)

Canonical file. Changing it needs a PR reviewed by BOTH people. Changes are ADDITIVE only (new optional fields, bump the minor
note below); a breaking change means a new `schema_version` (`m2.harvest.v2`) and a new folder name.

## Roles
- **Producer (Prabhav):** runs the models through Ollama and writes harvest part files. Does NOT score, label or compute features.
- **Consumer (Shaurya):** validates, scores (with the frozen Phase 5 scorer), labels and builds features. Never calls Ollama.

## The input list (what to generate for)
`ml/train_m2/contract/harvest_inputs.jsonl`: 321 lines, one per distinct model input. Fields: `input_key` (canonical JSON, same
function as `ml.mutation_engine.dataset_io.input_key`), `record` (the exact finding record Phase 5 used for that input: pass it
to `ml.train_m1.prompt.user_message`), `sets` (which Phase 5 sets contain it, with counts). Do not edit this file.

## Profiles (how to sample). 8 samples per input per generator per profile.
| Profile | sample 0 | samples 1-7 | Purpose |
|---|---|---|---|
| A | temperature 0.0, seed 0 | temperature 0.7, seed = sample_idx, top_p left at the Ollama default (`top_p: null`) | Identical to Phase 5's call, plus logprobs. Lets us cross-check against the existing candidate logs |
| B | temperature 0.0, seed 0 | temperature 1.0, top_p 0.95, seed = 1000 + sample_idx | More diverse candidates, so M2 sees more natural mistakes |

Everything else (system prompt, Patch-IR JSON-schema `format`, `num_predict`) is exactly as in `ml/train_m1/eval/ollama_client.py`.

## Generators
`zeroshot` (base model `qwen3.5:4b` with the same prompt and schema), `sft` (`argus-m1-sft`), `rft` (`argus-m1-rft`),
`rft_v2` (the repaired model, when it exists).

## Files
`ml/train_m2/harvest_out/<generator>/<profile>/part-<NNNN>.jsonl` (git-ignored). Exchanged through the shared Drive folder
`argus/m2_harvest/` with the same relative paths. Each (generator, profile) folder also gets `MANIFEST.json`
(copied into git under `ml/train_m2/harvest_manifests/<generator>_<profile>.json`) listing each part's sha256, line count,
the Ollama version, the model digest and the exact command used.

## One line = one generation
Validated by `harvest_line.schema.json` (this folder). Key rules:
- `tokens` is the full list of generated tokens: `t` text, `lp` natural-log probability, `top` the top-k alternatives as
  `[[token, logprob], ...]` or `null` if the server did not return them. Concatenating every `t` must equal `content`
  (Shaurya's validator checks this).
- On a request failure: `error` is a string, `content` is "", `tokens` is `[]`. Failures are recorded, never dropped.
- Exactly one line per (`input_key`, `generator`, `profile`, `sample_idx`); duplicates are a validation error.
- Part files are append-only and written one line at a time with flush + fsync, so an interrupted run can resume.

## Acceptance for a delivery
`python -m ml.train_m2.validate_harvest --root ml/train_m2/harvest_out` (Shaurya's tool) passes: schema, completeness
(321 inputs x 8 samples per generator-profile), duplicate check, text-equals-tokens check, manifest hashes. A delivery that fails
is returned with the list of problems.
