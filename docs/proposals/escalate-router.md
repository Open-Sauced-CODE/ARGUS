# Proposal: a deterministic escalate router (H6)

Author: Prabhav (Role C). For: the whole team. Decision needed from: Shaurya. Frozen files touched by this note: none.

## 1. Problem (measured)
Four rules have route ESC in `ml/README_contracts.md`: `dpdp.rule6a_rds`, `dpdp.rule6_account_mfa`, `dpdp.rule7_detection`,
`dpdp.rule15_region`. For them the only correct answer is the `escalate` operation. We measured how each generator behaves:

| Generator | Real RDS findings (C_verifier 51, gold 9) | A_val pass@1 | B1 pass@1 | C_verifier fix cases |
|---|---|---|---|---|
| SFT (`argus-m1-sft`) | escalates 0 of 51, tries a fix every time (recall 0.00) | 96.7% (349/361) | 96.2% | 414 of 415 |
| RFT-v1 (`argus-m1-rft`) | escalates 51 of 51 and 9 of 9 gold, 0.00% unsafe | 79.5% | 61.7% | about 365 |

So today we must choose between a model that never escalates and a model that escalates but loses 17 points of fix accuracy
(RFT-v1 also collapsed to 1.00 distinct answers, which makes best-of-N useless). The per-set, per-rule true/false positives and negatives
for every generator are in `docs/proposals/escalate-stats.md`, generated by the command in section 7.

Why the model is the wrong tool here: the escalate decision for these rules depends only on WHICH RULE fired, which the pipeline already
knows. The airlock projects only the fields that rule reads, so the model's input for an ESC rule is almost always the same few strings
(the RDS rule has 2 distinct train inputs). Asking a 4B model to re-derive a lookup is both unnecessary and unreliable.

## 2. Proposal
In the Phase 7 pipeline, before calling any generator, look up the rule's route in the table that `README_contracts.md` already defines:
- route ESC: build a fixed Patch-IR (`ops: [{"op": "escalate", "reason": "<fixed reason string per rule>"}]`, `rationale_ref` = the rule id),
  skip T0, M1 and the gate's fix checks, and send it straight to the human approval queue (T3) with the reason shown;
- route T0: the template; route M1: the model, called only for T0-miss FIX rules.
Effect: the pipeline escalates 100% of ESC findings by construction, and SFT keeps its 96.7% fix accuracy because it is never asked an
escalate question. No retraining is needed for this behaviour.

## 3. What it changes
- Phase 7 pipeline order: one route lookup at the front (a dictionary, no model call).
- T0: `remediate/templates/__init__.py` is frozen; adding ESC templates there is a frozen-file change that needs BOTH people. The router
  can live in a new Phase 7 module instead, which avoids touching it.
- M2: escalations bypass it, as designed (there is no model confidence to calibrate for a rule-based escalation).
- Dashboard: the approval queue shows the fixed reason ("needs a human: enabling account MFA cannot be done by a patch").
- RFT-v2: its escalation target becomes "also correct when asked", not the only safeguard.

## 4. Risks
- A new escalate-worthy rule that is not in the table is never escalated. Mitigation: a test that every rule in `policy/` has an explicit
  route, and that the route table equals the contracts table (`ml/tests/test_contracts_doc.py` already checks table vs rules).
- The model's own escalation judgement is no longer exercised. If we still want to report it, measure it separately (the `eval_v2` and
  `escalate_stats` tools do this on the harvest) and label it "model judgement, not the shipped behaviour".
- Over-escalation is impossible for fix rules (they never reach the router branch), so there is no new false-positive risk.

## 5. Test plan
1. Unit: every rule id in the route table returns the expected branch; an unknown rule id raises (fails closed to the human queue).
2. Unit: for every ESC rule the router returns a Patch-IR that validates against `remediate/patch_ir/schema.json` and passes the gate stub as 'escalated'.
3. Integration: replay the 321 harvest inputs through the router; ESC cases escalate 100%, fix cases never do.
4. Regression: SFT's A_val pass@1 on fix rules is unchanged (349/361 reproduces with `eval_v2`).
